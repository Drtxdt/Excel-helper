# 存档一致性与排错

## 数据约定

`src/storage.ts` 提供存储服务工厂与页面共用实例。连接首次使用时打开并复用；连接失败可重试。读取、日志恢复、保存、导入和导入前备份读取都进入同一队列。队列中的一次失败不会阻断后续工作。

`records` 仍存放原有 LearningRecord，数据库结构版本仍为 1。`settings/revision-state` 保存数据代次 generation，以及各关卡的 revision、writer、sequence。修订号在同一代次内递增；导入整体增加代次并重置关卡修订。两个字段共同判断新旧，updatedAt 只用于展示和无修订号的旧日志迁移。

保存调用立即解析并复制记录，之后才排队，避免等待期间引用对象被修改。写入事务同时读取修订状态、核验预期版本、保存记录和更新修订。事务内部只等待 IndexedDB 请求，不插入网络、计时器或其他任意异步任务。

待保存日志键为 `supply-station-pending:<会话 UUID>:<关卡 ID>:<操作序号>`。每个操作使用独立键，清理时仍确认会话和序号，既不靠毫秒时间戳，也不使用跨标签页不原子的“读旧值再删共享键”。日志提交后清除；事务失败则留下用于下一次读取时恢复。已应用的操作幂等清除，旧代次日志丢弃，有修订冲突的日志不覆盖数据库。

旧的 `supply-station-pending` 键仅在首次导入前迁移，且必须比数据库中的旧记录更新。它没有历史修订号，无法重建旧版本已经丢失的并发关系。导入后不允许这类旧日志复活。损坏日志单独隔离，不阻断其他关卡读取。localStorage 不可用时仍尝试 IndexedDB，但此时无法承诺在事务提交前关闭页面仍能恢复。

## 导入与多标签页

导入先解析校验，再进入写队列。它等待之前的保存结束，并在同一读写事务内保存 `before-import`、替换全部记录、增加代次。失败会中止事务，包括已执行的 clear 和备份更新；成功后才清理旧代次日志。仍在旧代次的保存请求会失败，不能覆盖导入结果。备份继续使用原有 version 1 格式，内部修订字段不导出。

跨页通知使用 BroadcastChannel，辅以 storage 事件和窗口重新获得焦点时的版本检查。通知只提示冲突，不把另一页的工作簿自动合进当前内存。事务内版本校验才是防止覆盖的最终保障，即使通知延迟，旧写入也不能穿过校验。页面保留当前内存作答供导出；点击“重新载入已保存记录”或手动刷新，才明确采用数据库版本。

冲突提示按整个学习记录集合处理，因此另一页更新其他关卡也可能要求重新载入。这是有意保守的选择，避免导出或导入时误以为本页持有完整的最新集合。冲突后的未提交作答应在重载前导出。不要指望两个标签页同时编辑后自动合并。

任何通过都设置 completed；只有未使用帮助的变式通过才新增 mastered。旧备份、数据库记录与旧日志中的 mastered=true/completed=false 会规范为两者都为 true，不撤回已经获得的掌握记录。课程版本改变时沿用已有策略：保留完成记录，不加载不匹配版本的草稿。

## 验证与边界

- `tests/storage-concurrency.test.ts` 使用 fake-indexeddb 的真实事务调度、连接门闩和原生 abort，覆盖快照时机、连续/跨关卡/同毫秒写入、导入期间旧请求、跨页修订冲突、失败回滚、刷新日志恢复、旧格式与不可用存储。
- `tests/state.test.ts` 检查初次读取去重、内存作答保留、冲突提示及导入结果更新。
- `e2e/storage.spec.ts` 通过真实界面验证先完成变式，以及同一浏览器两个标签页中的导入、冲突、继续编辑、导出和主动重载。测试生成的作答和截图仅放在忽略目录/短期 CI artifact。
- IndexedDB 对重叠作用域的读写事务按创建顺序串行执行；本轮没有复现“后创建的写事务先提交”。确认并修复的风险是异步之后才复制快照、共享待保存键、导入缺少代次隔离及通过变式未补齐完成状态。不要把防御性测试写成曾经发生过的用户数据事故。
- 真实浏览器验证范围为 Chromium；WebKit、平板触摸、操作判题及真实 Excel 对照仍按后续 PR 处理。浏览器清理站点数据、磁盘故障或用户未导出就明确刷新冲突页面，不在自动恢复保证范围内。

回退前先从学习记录页面导出 JSON；不要直接清除站点数据。旧代码忽略新修订字段且不具备并发保护，回退时应关闭其他标签页并保留导出文件。私人学习存档不进入 Git。
