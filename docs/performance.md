# 生产性能基线

本报告只描述本机生产构建实测，不代表所有电脑或真实平板。课程、案件计算仍使用 Univer；没有把参考答案写入应用接口，也没有跳过变式。

## 复现

固定 Node 24、pnpm 10.33.0 和锁文件，安装 Playwright Chromium。运行 `pnpm check`，在一个终端运行 `pnpm exec vite preview --host 127.0.0.1 --port 4173 --strictPort`，另一个终端运行 `pnpm perf:measure`。默认五轮，每轮新建浏览器上下文，依次进入课程 02、07、26、33、40 与首案对账。通过真实地址栏和公式栏填写解法，等待重算完成，每项连续检查三次，离开至学习记录页检查 Worker、画布和 DOM 数量。

输出默认 `outputs/pr06/performance.json`；用 `PERF_OUTPUT` 改名，`PERF_SAMPLES` 改轮数。设置 `PERF_TRANSFER=1` 补测首案两份单据，先真实完成对账再进入调拨。性能测量与其他浏览器测试、构建分开运行。

探针仅在 `?perf=1` 启用，PerformanceEntry 不含公式、单元格或学习记录，单项最多保留 200 条。正常使用不触发额外重算等待。测量含义：

- `navigation-ready`：测试端导航到写入按钮可用，包含页面加载和自动化等待；第一次新浏览器冷打开只有一个样本，不把它当大样本分布。
- `ready`：工作簿创建到计算完成与可编辑，不包含路由资源下载。
- `worker-init`：创建判题 Worker 到模块加载完成的 ready 消息。
- `recalculate`：真实写入命令开始到引擎计算结果已应用；包括事件、快照与消息往返，包含首次编辑样本。
- `check/first`、`check/warm`：第一次检查与同工作台后两次检查，包含等待计算、快照、原始数据及全部变式。每项分别有 5、10 个样本。
- 资源释放只证明离开时已观察到的 Worker、画布消失和 DOM 数量未逐次增长，不声称做过完整堆内存泄漏审计。

基线源码为 PR 05 的 `468a0b315dada91983e23003a31312362bc2cdd7`。在独立检出中复制本 PR 的 `perf` 目录，执行 `git apply --ignore-space-change perf/baseline-probes.patch` 添加相同测量点，再构建和运行脚本。不要在日常作答页面执行测量。补丁已用原始提交文件检查可应用。

## 门禁

`pnpm check` 最后执行资源体积检查：`dist/assets` 未压缩总字节数不得超过记录基线的 110%。这不是网络传输大小；不把 gzip 与原始体积混比。超限时必须分析并提供测量，不自动上调基线。

`node perf/compare.mjs <基线.json> <本次.json>` 要求 Node、系统、CPU、浏览器、视口和轮数相同。任何可比 p95 增长超过 20%、体积超限、残留 Worker/画布都会返回失败，要求复测和解释。100ms 重算、1 秒热检查是独立目标，未达到仍如实显示，不能通过改基线把目标改绿。Windows 耗时不能直接作为 GitHub Linux 耗时阈值；CI 固定执行体积门禁和功能回归，耗时比较需同环境测量。

## 测量结果

测量日期 2026-10-24，Windows、Intel Core i9-13900HX、Node 24.18.0、Chromium 156.0.8078.4、1366×768，未模拟弱网或 CPU 降速。最终应用源码提交 `834a676`。原始数据：[基线](../perf/results/baseline.json)、[最终复测](../perf/results/final.json)、[比较结果](../perf/results/comparison.json)。源码优化只有工作台内复用判题 Worker；每次判题的各份工作簿仍由 headless 层新建并销毁。取消、错误、过期返回、退出工作台都会释放 Worker。没有因性能目标删去课程检查或变式。


| 任务 | 热检查基线 p95（ms） | 最终 p50 / p95（ms） | 编辑重算 p50 / p95（ms） |
|---|---:|---:|---:|
| 02 | 1211.3 | 602.0 / 622.0 | 35.4 / 253.1 |
| 07 | 1162.4 | 601.4 / 625.5 | 37.4 / 55.3 |
| 26 | 1190.8 | 598.8 / 631.2 | 55.8 / 59.8 |
| 33 | 1055.9 | 599.8 / 639.6 | 55.8 / 57.6 |
| 40 | 1323.8 | 611.1 / 640.8 | 37.1 / 54.9 |
| case-017 | 1521.1 | 611.0 / 660.5 | 44.7 / 62.1 |

各项热检查均达到 p95 ≤ 1 秒。第 02 关重算 p95 仍高于 100ms，首次冷打开后的一个样本约 253ms；其余项目在这轮复测低于 100ms，不删除长尾样本。每项重算样本数分别为 5、15、5、5、55、100，p95 使用最近秩法；小样本不代表稳定的总体分布。

资源总量从 18,482,505 增至 18,497,813 bytes（+0.083%），没有超过 10% 门槛。所有可比 p95 均未超过基线 120%。30 次离开工作台的观察中，Worker=0、canvas=0；学习记录页 DOM 元素数范围为 243–244。

工作簿 ready 与导航、Worker 初始化的逐项 p50/p95 均在原始 JSON 的 summary。cold-browser 只有一个样本，fresh-context 有四个；同页每种路线有五个，不混称为五次冷启动。性能报告不替代真实 Excel 对照、真实 iPad/Android 或用户试用，本轮没有新增这三类实测。

较早一次优化复测的[原始数据](../perf/results/initial-optimized.json)也保留：当时首案重算 p95 为 115.8ms，说明这一目标受缓存、事件与系统调度影响，不能以最终一轮达标宣称所有使用场景都达标。该次工作树尚未完成后续导出校验和文案拆分，仅作为重复测量记录；验收主表采用最终应用提交。

## 首案完整两阶段补测

[补测原始数据](../perf/results/transfer.json)在每个新上下文先完成对账，再解锁调拨，五轮、每阶段三次检查。对账热检查 p50/p95 为 634.7/685.3ms，调拨为 618.9/663.6ms。冷打开案件的首次检查 p95 为 1340.2ms，调拨首次检查为 1077.8ms；1 秒目标针对热检查，不把冷启动也写成达标。

调拨写入重算共 20 个样本，p50/p95 为 64.1/111.9ms。补测 10 次离开调查桌后 Worker、canvas 均为 0。此阶段没有 PR 05 前后对照数据，只报告最终版本绝对耗时。
